PART 9 - RAG WITH POSTGRESQL AND PGVECTOR (IMPLEMENTED)
================================================================================

9.1 Objective

Part 9 adds Retrieval-Augmented Generation (RAG) to SmartResolve. The system
searches verified internal knowledge before asking Llama 3.2 to generate an
answer.

9.2 Models

- llama3.2 generates the final chat and RAG response.
- mxbai-embed-large converts article content and employee questions into
  embedding vectors for similarity search.

Install the models with:

  ollama pull llama3.2
  ollama pull mxbai-embed-large

9.3 Knowledge Article Storage

Verified articles are stored in the knowledge_articles table. An administrator
or active support engineer creates an article through:

  POST http://localhost:8080/api/knowledge/articles

Example body:

  {
    "title": "Frequent Wi-Fi disconnections on Windows laptop",
    "content": "Update the Wi-Fi adapter driver, restart WLAN AutoConfig, forget the wireless network, and connect again.",
    "sourceTicketId": null
  }

The service validates the user, saves the article with verified=true and
active=true, and indexes it in the vector store.

9.4 Vector Storage

Spring AI stores embeddings in PostgreSQL using pgvector. The vector table is:

  smartresolve_knowledge_vectors

Configuration:

  spring.ai.vectorstore.pgvector.initialize-schema=true
  spring.ai.vectorstore.pgvector.dimensions=1024
  spring.ai.vectorstore.pgvector.distance-type=COSINE_DISTANCE
  spring.ai.vectorstore.pgvector.index-type=HNSW
  spring.ai.vectorstore.pgvector.table-name=smartresolve_knowledge_vectors

9.5 RAG Chat Endpoint

Employees use:

  POST http://localhost:8080/api/ai/rag/chat

Example body:

  {
    "conversationId": null,
    "message": "My Windows laptop disconnects from Wi-Fi frequently. What should I do?"
  }

The service creates an embedding for the question, searches pgvector, selects
up to five relevant documents with a similarity threshold of 0.60, and filters
for verified=true and active=true.

9.6 Prompt and Response Flow

1. RAGController receives the authenticated request.
2. RAGService validates the user and conversation ownership.
3. The question is searched in the PostgreSQL vector store.
4. Relevant article text and metadata are retrieved.
5. The retrieved knowledge is added to the system prompt.
6. Previous messages are loaded using the conversation ID.
7. Spring AI sends the prompt, retrieved context, and question to Llama 3.2.
8. The response and retrieved sources are returned to the employee.

The LLM receives:

  System instructions
  + Retrieved verified knowledge
  + Previous conversation messages
  + Current employee question

The embedding model only performs vector generation. Llama 3.2 generates the
final answer.

9.7 RAG Memory

RAG chat uses the existing JDBC conversation memory:

- chat_conversations stores the owner, title, and timestamps.
- SPRING_AI_CHAT_MEMORY stores user, assistant, system, and tool messages.

The same conversationId must be used for follow-up questions. Sending null
creates a new conversation.

9.8 RAG Response

A successful response contains:

  {
    "conversationId": "RAG_CONVERSATION_ID",
    "answer": "You should update the Wi-Fi adapter driver and restart the WLAN AutoConfig service.",
    "sources": [
      {
        "articleId": "KNOWLEDGE_ARTICLE_ID",
        "title": "Frequent Wi-Fi disconnections on Windows laptop",
        "sourceTicketId": null
      }
    ],
    "timestamp": "2026-11-15T17:15:00"
  }

The sources list identifies the verified articles used for the answer.

9.9 Implemented Components

- KnowledgeArticleController creates and lists verified articles.
- KnowledgeArticleService validates, saves, and indexes articles.
- RAGController exposes the RAG chat endpoint.
- RAGService retrieves documents, builds prompt context, and calls the LLM.
- KnowledgeArticle represents relational knowledge article data.
- VectorStore stores and searches pgvector embeddings.
- ChatMemory maintains conversation history.

9.10 Database Verification

  SELECT id, title, verified, active, verified_by, created_at
  FROM knowledge_articles
  ORDER BY created_at DESC;

  SELECT id,
         metadata->>'articleId' AS article_id,
         metadata->>'title' AS title,
         metadata->>'verified' AS verified,
         metadata->>'active' AS active
  FROM smartresolve_knowledge_vectors;

  SELECT conversation_id, type, content, "timestamp"
  FROM spring_ai_chat_memory
  WHERE conversation_id = 'RAG_CONVERSATION_ID'
  ORDER BY "timestamp" ASC;

9.11 Part 9 Result

Part 9 is implemented. SmartResolve can store verified knowledge articles,
create embeddings with mxbai-embed-large, retrieve relevant articles with
PostgreSQL pgvector, add the retrieved knowledge to the Llama 3.2 prompt, and
return an answer with its knowledge sources.

1. PROJECT OVERVIEW

1.1 Introduction

SmartResolve is an AI-powered IT Support Ticket Management
System developed using Java and Spring Boot. The primary objective of this
application is to simplify and improve the management of IT support requests
through automation, artificial intelligence, centralized ticket management, and
structured support workflows.

In a traditional IT support environment, employees report
technical problems to the IT department. Support teams manually review these
requests, identify their categories and priorities, assign them to appropriate
engineers, investigate the problems, and provide resolutions.

This process can involve repetitive manual work, delayed
responses, inconsistent ticket categorization, and repeated troubleshooting of
previously resolved problems.

SmartResolve addresses these challenges by integrating a
locally hosted Large Language Model (LLM) with the Spring Boot backend.

The application allows employees to create support tickets,
receive AI-generated recommendations, communicate with the AI assistant, and
track the progress of their requests. Administrators and support engineers can
review AI recommendations, manage ticket assignments, communicate with
employees, and update ticket statuses.

The system is designed around a human-in-the-loop approach.
Artificial intelligence provides recommendations and assistance, while
authorized human users retain control over important operational decisions.

12. PART 9 â€“ RETRIEVAL-AUGMENTED GENERATION (RAG) WITH
PGVECTOR

12.1 Objective

The objective of Part 9 is to enhance SmartResolve by
allowing the AI assistant to retrieve relevant information from previously
resolved support tickets.

RAG stands for Retrieval-Augmented Generation.

It combines two capabilities:


 Retrieval:
     Finding relevant information from an existing knowledge source.
 Generation:
     Using the retrieved information to generate a contextual response through
     an LLM.


This part is designed as an extension to the existing AI
analysis and chat functionality.

12.2 Why RAG Is Required

A general-purpose LLM does not automatically know the
internal history of the SmartResolve application.

For example, suppose the support team has previously
resolved several Wi-Fi issues.

The solutions may be stored in PostgreSQL, but Llama 3.2
will not automatically know those records.

RAG allows the application to retrieve relevant historical
information and provide it to the model as additional context.

This can reduce repeated troubleshooting and improve the
relevance of AI recommendations.

12.3 What Is an Embedding?

An embedding is a numerical representation of text.

An embedding model converts a sentence or paragraph into a
vector containing numerical values.

For example:

Input:

&quot;My laptop Wi-Fi is not working.&quot;

Illustrative vector:

[0.12, 0.87, 0.34, 0.56, ...]

A previous ticket description and its verified solution can
also be converted into a vector.

The application compares vectors to identify semantically
similar information.

This means that sentences with similar meanings can be
retrieved even when they use different words.

12.4 Embedding Model

The chat-generation model and embedding model have different
responsibilities.

Llama 3.2

Responsible for:


 Understanding
     user queries.
 Generating
     responses.
 Creating
     ticket recommendations.
 Explaining
     retrieved solutions.


Embedding Model

Responsible for:


 Converting
     ticket descriptions into vectors.
 Converting
     verified solutions into vectors.
 Supporting
     semantic similarity search.


An example Ollama embedding model is:

nomic-embed-text

It can be downloaded using:

ollama pull nomic-embed-text

The selected embedding model and its vector dimensions must
remain consistent for all stored vectors and future searches.

12.5 Why pgvector?

pgvector is a PostgreSQL extension that adds vector storage
and similarity search capabilities.

Instead of maintaining a separate vector database,
SmartResolve can use PostgreSQL for both relational data and vector data.

Benefits include:


 Integration
     with the existing PostgreSQL database.
 Vector
     similarity search.
 Storage
     of ticket references alongside embeddings.
 Reduced
     infrastructure complexity for the initial implementation.


12.6 Ticket Embedding Storage

A proposed additional table is:

ticket_embeddings

Important fields:


 id
 ticket_id
 content
 embedding
 created_at


The ticket_id field references the original support ticket.

The content field contains the searchable text, such as:


 Ticket
     title.
 Ticket
     description.
 Verified
     resolution notes.

     troubleshooting information.

12.7 RAG Processing Flow

The proposed RAG workflow is:


 A
     support engineer resolves a ticket.
 The
     resolution is reviewed and marked as suitable for reuse.
 The
     backend combines the relevant ticket details and verified solution.
 The
     embedding model converts this text into a vector.
 The
     vector and associated ticket reference are stored in PostgreSQL using
     pgvector.
 A
     new employee creates a similar support ticket.
 The
     backend generates an embedding for the new problem.
 Vector
     similarity search retrieves the most relevant previous tickets.
 The
     backend retrieves their verified solutions.
 The
     retrieved information is added to the LLM prompt.
 Llama
     3.2 generates a response using both the current ticket and retrieved
     knowledge.
 The
     AI recommendation is saved for human review.

The model can then generate a more relevant troubleshooting
recommendation based on the previous verified resolution.

18. SECURITY AND RELIABILITY CONSIDERATIONS

Security is important because SmartResolve handles employee
information and internal IT support requests.

The following controls should be maintained:


 Passwords
     must be stored using BCrypt hashing.
 Protected
     APIs must require authentication.
 Authorization
     must be enforced in the backend.
 Employees
     must only access their own tickets.
 Internal
     comments must remain restricted.
 Conversation
     history must respect ownership and access permissions.
 AI
     recommendations must be validated before applying them.
 The
     LLM must not directly access or modify the database.
 Sensitive
     information must not be included unnecessarily in AI prompts or
     embeddings.
 Ticket
     status changes must follow valid business transitions.
 Important
     ticket operations must be recorded in history.
 Database
     credentials and JWT secrets must not be committed to source control.
 AI-generated
     output must be treated as untrusted input and validated.
 Production
     deployment should use HTTPS and secure secret management.

20. CONCLUSION

SmartResolve is designed to combine conventional IT service
management functionality with modern artificial intelligence capabilities.

The initial application architecture establishes secure
authentication, ticket management, role-based authorization, AI-powered ticket
analysis, human-reviewed recommendations, and conversational assistance.

Spring Boot provides the backend foundation, PostgreSQL
manages structured application data, Spring Security and JWT protect
application endpoints, and Spring AI connects the backend with the locally
hosted Llama 3.2 model through Ollama.

The conversation memory functionality enables the AI
assistant to maintain context across multiple messages.

The planned RAG extension introduces semantic retrieval of
previously resolved support tickets using embeddings and PostgreSQL with
pgvector. This will allow the AI assistant to use historical, verified support
knowledge when generating recommendations for new incidents.

The overall design follows a human-in-the-loop approach: AI
assists employees and support teams, while authorized human users remain
responsible for approving recommendations, assigning engineers, performing
troubleshooting, and resolving tickets.

The intended outcome is a centralized, secure, extensible,
and AI-assisted IT support platform that improves the efficiency of ticket
handling and encourages the reuse of organizational troubleshooting knowledge.
